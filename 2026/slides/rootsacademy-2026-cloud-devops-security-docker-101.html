Block 02 · 60 minutes

Containerization

Docker, the layer model, and why your image is a gigabyte when it should be a hundred megabytes.

How we got here

Bare metal, virtual machines, containers, functions
1990s

Bare metal

One app, one physical server. Ordered months ahead. Used at 10 percent. "It works on that machine" and nowhere else.

2000s

Virtual machines

Many guest OSes on one host. Better use of hardware. Each VM still carries a full operating system, so it boots in minutes and weighs gigabytes.

2013+

Containers

Share the host kernel, isolate the process. Starts in under a second, weighs megabytes, and ships the dependencies with the app.

2014+

Functions

You give up the machine entirely and hand over a function. Scales to zero. You lose control over the runtime.

Each step trades control for speed and density. Containers are the current sweet spot for most data and AI workloads, which is why the rest of this block is about them.

What is a container?

An isolated process, not a small computer

Virtual machine

  • Virtualises hardware
  • Has its own guest kernel
  • Boots in minutes, sized in gigabytes
  • Strong isolation boundary
  • Patch the OS inside it, forever

Container

  • Virtualises the operating system
  • Shares the host kernel
  • Starts in under a second, sized in megabytes
  • Weaker isolation: same kernel
  • You replace it instead of patching it
  • A container is one or more processes with their own view of the filesystem, network and process table
  • Linux gives this with namespaces (what the process can see) and cgroups (how much it can use)
  • On your Mac, Docker runs a small Linux VM. Containers are a Linux feature
  • The "shares the kernel" point matters later for security: a container escape is a host compromise. Do not run untrusted code in a container and call it sandboxed.

What is Docker?

The tooling that made containers usable
  • Open-source project that builds, runs and distributes containers in a standard format
  • Containers existed before Docker. The standard format and the developer experience are what changed the industry
  • It also runs the largest public registry, hub.docker.com
  • The format is now an open standard (OCI), so other tools read and write the same images:
    • Podman, containerd, BuildKit, Buildah
    • Every cloud registry: ECR, ACR, Artifact Registry

The promise

"It works on my machine" becomes true everywhere, because the machine travels with the app.

The same image runs on your laptop, in CI, on ECS, and in Kubernetes. Nothing is rebuilt on the way.

Three words you must not mix up

Dockerfile, image, container
Recipe

Dockerfile

A text file with build instructions. Lives in git next to your code. Reviewed like any other code.

Artifact

Image

The built result: a read-only, immutable stack of layers plus metadata. You push this to a registry and tag it.

Process

Container

A running instance of an image, with a thin writable layer on top. Disposable. Many containers from one image.

Dockerfile— build → image— run → container
A class is not an object. A Dockerfile is not an image, and an image is not a container. Interviewers ask this.

The three verbs

Build, push, run
# build a local image from the recipe, and tag it
$ docker build -t my-app:1.2.0 .

# log in to the registry and distribute the image
$ REGISTRY=$ACCOUNT.dkr.ecr.eu-west-1.amazonaws.com
$ aws ecr get-login-password --region eu-west-1 \
    | docker login --username AWS --password-stdin $REGISTRY
$ docker push $REGISTRY/my-app:1.2.0

# run it, map a port, pass configuration
$ docker run --rm -p 8000:8000 -e LOG_LEVEL=debug my-app:1.2.0

# the four commands you will use while debugging
$ docker ps                      # what is running
$ docker logs -f <container>      # what it is saying
$ docker exec -it <container> sh   # get a shell inside it
$ docker image ls                # what you have built, and how big it is
Configuration comes in from the outside with -e or a file. An image that must be rebuilt to change an environment is a broken image.

Anatomy of a Dockerfile

Seven instructions cover almost everything
FROM  python:3.12-slim        # the base you start from
WORKDIR /app                    # cd, for every later step
COPY  requirements.txt .       # bring files in
RUN   pip install --no-cache-dir -r requirements.txt
COPY  src/ ./src/
ENV   PYTHONUNBUFFERED=1       # runtime config default
EXPOSE 8000                    # documentation, not a firewall
USER  app                      # stop running as root
ENTRYPOINT ["python", "-m", "src.main"]

Two things people get wrong

  • CMD alone is a complete default command, overridden by docker run <image> <args>. ENTRYPOINT is a fixed prefix that always runs, and it turns CMD into default arguments. Convention: ENTRYPOINT for the binary, CMD for the flags
  • Use the exec form ["python","app.py"]. The shell form receives SIGTERM and does not pass it on, so your container is killed hard on every deploy. Also handle SIGTERM in your code, or run with --init
  • EXPOSE publishes nothing by itself. Only -p does, or -P, which publishes everything EXPOSE lists

Block 02b · 35 minutes · new this year

Layers and image size

The single most common Docker task on a real project is making somebody else's image smaller and faster to build.
Your image is 1.4 GB
and the build takes 9 minutes
The app is one Python file. Nobody wrote it that way on purpose. It grew, one line at a time, and nobody looked at the number.
  • This is the real-world hook. Say honestly: you will be handed this image in your first months, and fixing it is a visible early win.

Why size and build time matter

Four costs, all of them paid repeatedly

Speed

Every CI run pulls and pushes the image. Every scale-out pulls it again. A gigabyte on a cold node is minutes of waiting.

Cold starts

ECS and Kubernetes pull the whole image before your code runs, so size becomes user-facing latency. Lambda streams only the chunks it needs, so it suffers less, but the 10 GB cap is real.

Money

Registry storage, cross-region data transfer, and CI minutes. Small on one image, real across hundreds of builds a day.

Attack surface

Every package in the image is a package that can have a CVE. A build compiler in production is a tool for an attacker.

Small images are not about tidiness. They are faster, cheaper and safer, and the fix is usually 10 lines of Dockerfile.

An image is a stack of layers

Each instruction that changes the filesystem adds one layer
FROM python:3.12-slim~150 MB
WORKDIR /app0 B · metadata only
COPY requirements.txt .2 KB
RUN pip install -r requirements.txt~420 MB
COPY src/ ./src/180 KB
ENV / USER / ENTRYPOINT0 B · metadata only
container writable layercreated by docker run

What follows from this

  • Layers are read only and stacked in order. The image is the sum of them
  • RUN, COPY and ADD create layers. ENV, WORKDIR, USER, LABEL and ENTRYPOINT only write metadata
  • Layers are content-addressed, so two images on the same base share those bytes on disk and in the registry
  • docker run adds a thin writable layer. It disappears with the container. That is why data must go to a volume or to S3

Layers are cached, and the cache is ordered

One changed line invalidates everything below it
  • Before running an instruction, Docker checks whether it already has a layer for that instruction with those inputs. If yes, it reuses it in milliseconds
  • On the first miss, the cache is gone for every instruction after it. Order is everything
  • For COPY, the input is the content of the copied files. Change one byte in one file and that layer, and all later layers, are rebuilt

Cache hit

=> [2/5] WORKDIR /app          CACHED
=> [3/5] COPY requirements.txt  CACHED
=> [4/5] RUN pip install ...    CACHED
=> [5/5] COPY src/ ./src/       1.1s
Total: 3s

Cache miss on step 3

=> [2/5] WORKDIR /app          CACHED
=> [3/5] COPY . .              2.3s
=> [4/5] RUN pip install ...   184.0s
=> [5/5] COPY src/ ./src/      1.1s
Total: 3m 8s

Order your Dockerfile by change frequency

Rarely changing things first, your source code last
Slow: rebuilds on every commit
FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
ENTRYPOINT ["python","-m","src.main"]

Editing one line of Python changes COPY . ., so pip install runs again. Three minutes, every commit, for nothing.

Fast: dependencies cached
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY src/ ./src/
ENTRYPOINT ["python","-m","src.main"]

Dependencies only reinstall when requirements.txt changes. Normal commits rebuild the last layer only. Three seconds.

Same image, same result, same lines of code. Only the order changed. This is the highest-value Dockerfile habit you can build.

The deletion trap

Deleting a file in a later layer does not make the image smaller
Still 1.2 GB
RUN apt-get update
RUN apt-get install -y build-essential
RUN pip install -r requirements.txt
RUN apt-get remove -y build-essential
RUN rm -rf /var/lib/apt/lists/*
Actually smaller
RUN apt-get update \
    && apt-get install -y --no-install-recommends build-essential \
    && pip install --no-cache-dir -r requirements.txt \
    && apt-get purge -y build-essential \
    && apt-get autoremove -y \
    && rm -rf /var/lib/apt/lists/*
  • Layers only add. A delete in a later layer writes a marker that hides the file. The bytes stay in the earlier layer, and they still travel with the image
  • To remove something, remove it in the same RUN that created it
This applies to secrets too. A token you copied in and deleted three lines later is still in the earlier layer: anyone who can pull the image extracts it with docker save. And docker history exposes anything you passed as ARG or ENV.

Measure before you optimise

Find the fat layer instead of guessing
$ docker image ls my-app
REPOSITORY   TAG      IMAGE ID       SIZE
my-app       1.2.0    8a1f3c9d2e77   1.41GB

# which layer is the expensive one?
$ docker history my-app:1.2.0 --human --format "table {{.Size}}\t{{.CreatedBy}}"
SIZE      CREATED BY
612MB     RUN pip install -r requirements.txt
438MB     RUN apt-get install -y build-essential gcc g++
121MB     COPY . .                            <- the .git folder and the venv
9.13kB    COPY src/ ./src/
0B        ENV PYTHONUNBUFFERED=1

# byte-level view, and what is wasted
$ dive my-app:1.2.0
Rule: never optimise a Dockerfile you have not run docker history on. It lists layers in build order, not by size — pipe it through sort -h, or use dive.

The usual suspects, in the order you will find them

Choose your base image on purpose

The first line of the Dockerfile decides most of the size
python:3.12
~1.0 GB
python:3.12-slim
~150 MB
python:3.12-alpine
~55 MB
distroless/python3
~55 MB

Uncompressed, order of magnitude, before your own dependencies. Check the current numbers yourself.

Start with -slim

Debian, glibc, no documentation or extra tooling. Python wheels install normally. This is the sensible default for data and AI work.

Alpine: read the small print

Alpine uses musl, not glibc. The big scientific packages now ship musl wheels, but plenty of others do not, and PyTorch ships none at all, so pip compiles from source. Builds get slow, images can end up bigger, and musl's allocator can cost you numeric performance.

Distroless and scratch ship no shell and no package manager (the :debug tags do). Excellent for security and size, painful to debug, and distroless gives you Debian's system Python, not the version you pick. Use them when the service is stable.

Multi-stage builds

Build in a fat image, ship a thin one
# ---------- stage 1: build ----------
FROM python:3.12 AS builder
RUN apt-get update && apt-get install -y --no-install-recommends gcc
RUN python -m venv /opt/venv
ENV PATH=/opt/venv/bin:$PATH
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# ---------- stage 2: runtime ----------
FROM python:3.12-slim
WORKDIR /app
COPY --from=builder /opt/venv /opt/venv
ENV PATH=/opt/venv/bin:$PATH
COPY src/ ./src/
USER 1000
ENTRYPOINT ["python","-m","src.main"]

What happens

  • The compiler, the headers and the build caches live in stage 1 only
  • Only the named paths are copied forward. Everything else is thrown away
  • The final image holds the runtime, the installed packages and your code. Nothing else
  • Typical result on a real project: 1.4 GB down to 220 MB, and the same app

Copy a whole virtual environment, not loose packages. It keeps the console scripts and survives a Python version bump. The same shape works for compiled languages and for npm run build.

  • If they use uv or poetry, the same shape applies: install into a venv in the builder, copy the venv forward.
  • Mention docker build --target builder for debugging a failing build stage.

.dockerignore

Two minutes of work, often the biggest single win
.git
.github
.venv
venv/
__pycache__/
*.pyc
.pytest_cache
.mypy_cache
node_modules
data/
notebooks/
*.ipynb
.env
*.pem
README.md
Dockerfile
  • Everything in the build context is sent to the builder before the build starts. A 900 MB context makes every build slow, even a cached one
  • COPY . . without a .dockerignore is how .git, local virtual environments and sample data end up in production
  • Excluding .env and key files stops the most common accidental secret leak
  • Check it: docker build prints transferring context: ... B on the first line
If that number is more than a few megabytes, stop and fix the ignore file first.

Four more levers

Worth knowing once you have the basics

BuildKit cache mounts

RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

Keeps the download cache between builds without putting it in the image. Drop --no-cache-dir here: the two cancel each other out.

Build secrets

RUN --mount=type=secret,id=tok \
    pip install --index-url \
    "https://$(cat /run/secrets/tok)@pypi.acme.io/simple" -r req.txt
# docker build --secret id=tok,env=PYPI_TOKEN .

Mounted as a file at /run/secrets/<id> for that step only, and your command must read it. Never use ARG for a token.

Platform matters

docker build --platform linux/amd64 -t my-app .

Your Mac builds arm64; Lambda and most ECS tasks run amd64. This mismatch is the exec format error you meet in week one.

Pin and scan

FROM python:3.12-slim@sha256:0e1f...
docker scout cves my-app:1.2.0

A digest makes the build reproducible. A scan tells you what you are shipping. Both belong in CI.

Checklist: slimming an image

In this order, every time
  • 1 · Measure. docker image ls, then docker history. Write the number down
  • 2 · Fix the context. Write a .dockerignore. Check the transferred size
  • 3 · Fix the base. Move to -slim or distroless
  • 4 · Reorder. Dependencies before source code
  • 5 · Split. Add a builder stage, copy only the artifacts forward
  • 6 · Clean in place. No caches, and delete in the same RUN
  • 7 · Measure again. Compare with step 1, and put the number in the pull request
  • 8 · Keep it honest. Fail CI if the image grows past a threshold
Steps 2, 3 and 5 give you most of the win. Do those three and stop when the image is small enough. Perfect images are not the goal.

Block 03 · 25 minutes

Container orchestration

One container on your laptop is a demo. Production needs something to keep many of them alive.
Is Docker enough to run a reliable, scalable application?
  • How do you add scalability and redundancy to your containers?
  • How do you handle updating your containers without downtime?
  • How do you make the app inside a container reachable?
  • How do you manage many apps and many containers together?
  • These now reveal one by one as you press →/Space — let them answer before you show the next.
  • Answer: no. docker run gives you a process, not a system.

What an orchestrator does for you

The four questions, answered
QuestionWhat the orchestrator gives you
Scalability and redundancyRun N copies across machines, restart what dies, add copies when load rises
Updating without downtimeRolling updates, health checks, and an automatic rollback when the new version fails
ReachabilityService discovery and load balancing, so callers use a stable name instead of an IP address
Many apps togetherScheduling on shared machines, resource limits, isolation, and one place for configuration and secrets
You describe the desired state. The orchestrator keeps reality equal to it. This is the same idea as infrastructure as code, applied to running processes.

Kubernetes in one slide

The vocabulary you need to follow a conversation

Objects

  • Pod — one or more containers that always run together. The smallest unit
  • Deployment — "keep 3 pods of this image alive, and update them safely"
  • Service — a stable name and load balancer in front of pods
  • Ingress — how traffic from outside gets in
  • ConfigMap / Secret — configuration and credentials, injected at runtime. A Secret is base64, not encrypted
  • Namespace — a logical folder, not a security boundary on its own

How it works

  • You submit YAML that describes the desired state
  • A control loop compares desired with actual and fixes the difference, forever
  • That loop is why a deleted pod comes back and a scaled deployment stays scaled

The honest warning: Kubernetes is powerful and expensive to own. It is the right answer for many services and many teams. It is rarely the right answer for one Python job that runs nightly.

You will not always need Kubernetes

Pick the smallest runtime that fits the workload
AWS optionGood forWatch out for
LambdaEvents, short jobs, spiky traffic, glue code15-minute limit, cold starts, and the image needs the Lambda runtime client
ECS on FargateLong-running containers, no cluster to manageLess flexible than Kubernetes, AWS-specific
ECS Express ModeOne web service from one container, fastest pathLimited control over networking. App Runner is closed to new customers, use this instead
EKSMany services, many teams, portability, complex networkingYou now own a platform. Budget for that

ECS, EKS and Batch run the same OCI image unchanged, so the choice is a runtime decision, not a rebuild. Lambda is the exception: its image needs the Lambda runtime client baked in.

Cloud-native applications

Built for the platform, not moved onto it

Lift and shift

  • One large application on a few big VMs
  • State on local disk
  • Scaling means a bigger machine
  • Releases are events, with a runbook and a weekend
  • Configuration lives in files on the server

Cloud native

  • Small services in containers, managed by a platform
  • Stateless processes, state in managed services
  • Scaling means more copies, automatically
  • Releases are routine and reversible
  • Configuration comes from the environment
  • Logs, metrics and traces are built in, not added later
Migrating to the cloud without changing the design gives you the old problems with a new bill. The value comes from the second column.
Block 04 · 45 minutes

Agile, DevOps & CI/CD

How a change gets from your laptop to production, and the culture that makes that safe.

What is Agile?

Short feedback loops instead of long plans

Waterfall

Analyse, design, build, test, release. Each phase finishes before the next starts. You learn whether you built the right thing at the end, when changing it is most expensive.

Agile

Build a small slice, show it, learn, adjust. Repeat every one or two weeks. You learn continuously, and the plan is allowed to change.

  • The value is the feedback loop, not the ceremonies. Standups and sprints are the tools
  • Agile makes a promise it cannot keep alone: it can only deliver in two weeks if releasing takes minutes, not months
That gap between "the team is ready" and "the change is live" is exactly the gap DevOps closes.

What is DevOps?

"A set of practices intended to reduce the time between committing a change to a system and the change being placed into normal production, while ensuring high quality." Bass, Weber & Zhu — DevOps: A Software Architect's Perspective
Read it again and notice what is not in it: no tool, no job title, no cloud provider. Two things only — speed and quality, and the claim that you can have both.
Fun fact: the word is Belgian 🇧🇪. Patrick Debois (pictured) coined "DevOps" as a conference hashtag for the first DevOpsDays, in Ghent, in 2009.

DevOps is not about the tools

Three things it is not, and one thing it is

Not a tool

Buying Kubernetes and GitHub Actions does not make you a DevOps team. Tools support a way of working. They do not create it.

Not a role

A "DevOps engineer" who takes the deployment work away from developers has rebuilt the wall with a new job title.

Not a team

A separate DevOps department between Dev and Ops is the problem DevOps was invented to remove.

It is end-to-end responsibility

The team that builds it, ships it, monitors it and gets paged for it. Feedback from production reaches the person who can fix the cause. Everything else in this block exists to make that responsibility bearable.

  • If they push back ("but my client has a DevOps team"), agree. Describe the platform-team pattern: a team that provides paved roads, not a team that does your deploys.

Does it actually work?

Four measures, used across the industry

Deployment frequency

How often you release. Elite teams: on demand, many times a day. Low performers: once a month or less.

Lead time for change

Commit to production. Elite: under an hour. Low: one to six months.

Change failure rate

Share of releases that cause a problem. Faster teams are not less careful. They fail less.

Failed deployment recovery time

How fast you recover, called "time to restore" in older reports. Elite: under an hour. Small changes are easy to reverse.

These are the DORA metrics, from the yearly State of DevOps research. The classic finding was that speed and stability rise together, because each change is small and reversible. The recent reports complicate it: AI-assisted teams ship faster but are less stable, so the trade-off returns unless the delivery practices are strong.

So what is a DevOps engineer?

An enabler of the way of working
  • Builds and maintains CI/CD pipelines so other people can ship safely
  • Sets up monitoring, logging and alerting, so problems are seen before users report them
  • Makes testing and security checks part of the pipeline, not a separate gate
  • Improves infrastructure reliability: scaling, self-healing, cost, and recovery
  • Builds the paved road, then teaches people to use it

The honest note

Many companies lack the culture but want the label, so "DevOps engineer" is often used for what is really a cloud or infrastructure engineer.

Read the job description, not the title. Ask who gets paged at 3 a.m. The answer tells you whether the culture is real.

Every one of these is DevOps with a harder artifact to version. Learn the base discipline once, then add the domain problems.

Git branching models

How the team agrees to work together

GitFlow

Long-lived develop and main, plus release and hotfix branches. Built for stability and for software with versioned releases that customers install.

  • Long-lived branches drift, so merges get painful. Slow, and it fights continuous delivery

Trunk-based development

One main branch. Short-lived feature branches, merged within a day or two behind feature flags. Built for agility.

  • Small merges, few conflicts, fast feedback. Needs a strong CI pipeline. What most Dataroots projects use
  • Whatever the model: protect main, require a pull request, and require the pipeline to pass before merge
  • Every team does it slightly differently. Keep it as simple as the team allows

CI: continuous integration

Keep the team's code mergeable and healthy
What it answers
  • How does the team collaborate without blocking each other?
  • How do we keep code quality high without a manual reviewer for everything?
How
  • Merge small changes often, through pull requests
  • On every push, run automatically:
    • linting and formatting: ruff, terraform fmt
    • type checks: mypy
    • tests and coverage: pytest
    • security and dependency scans
    • build the artifact, so you know it still builds
  • Repository policies: protected main, required checks, required review
The point of CI is not the tests. It is that a broken change is found in minutes by a machine, not in a week by a colleague.

CD: two different words

Continuous delivery and continuous deployment

Continuous delivery

Every change that passes CI is ready to release, automatically deployed to a staging environment. Production still needs a human to press the button.

Where most client projects sit, and a good place to be.

Continuous deployment

Every change that passes CI goes to production, with no human step.

Needs real confidence: good tests, monitoring, feature flags and a fast rollback. Earn it, do not start with it.

commit→ build & test→ deploy to dev→ deploy to staging→ production
The environments are the same code with different variables. If dev and production differ by hand-made changes, you do not have a pipeline. You have a habit.

Anatomy of a pipeline

Two systems, one config file, four words
  • Version control stores the code and emits events
    • GitHub, GitLab, Bitbucket, Azure DevOps
  • Build system watches for events and runs the work
    • GitHub Actions, GitLab CI, Jenkins, Azure Pipelines
  • You define it in a config file, usually YAML, stored in the repository
  • Every tool works roughly the same way. Which one you use depends on the client
on:                        # TRIGGER: which events
  push:
    branches: [main]
  pull_request:

jobs:                      # JOB: runs on one machine
  test:
    runs-on: ubuntu-latest
    steps:                  # STEP: one thing at a time
      - uses: actions/checkout@v5      # pre-made ACTION
      - uses: astral-sh/setup-uv@v8
      - run: uv sync --frozen          # your own command
      - run: uv run pytest -q
  build:
    needs: test                        # ordering between jobs
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5      # every job starts empty
      - run: docker build -t my-app:${{ github.sha }} .

A real pipeline, end to end

What the exercise later today will look like
1 · On PRlint, type check, unit tests, build the image without pushing
2 · On merge to mainbuild the image once, tag it, push it to ECR
3 · Deploy to devterraform apply with the new image tag
4 · Smoke testcall the deployed endpoint and check the answer
5 · On git tagretag the same image, deploy to production

Note what is not happening

  • The image is built once. Later stages retag it, they do not rebuild
  • Nobody logs into a server
  • Nobody runs terraform apply from a laptop

Also worth having

  • Manual approval before production
  • Continuous testing at every stage, not only at the start
  • Release during business hours, when people are awake to fix it

Hard-won rules

Things every project learns the painful way
  • Never put secrets in code. Have the pipeline fetch them from a secret manager, ideally by reference at runtime rather than as environment variables, which leak into logs and docker inspect. Assume anything in git is public one day
  • Build the artifact once. Retag and promote the same image between environments. Rebuilding per environment means production runs bytes you never tested
  • Pin your versions. Actions, base images, dependencies. Prefer a digest over a tag. A floating latest is a build that breaks on a day you changed nothing
  • Use matrix builds when it matters: several Python versions, several platforms
  • Add a smoke test after every deploy. One call that proves the thing is alive catches most bad releases in seconds
  • Keep the pipeline fast. A pipeline over 10 minutes gets worked around, and a pipeline people work around protects nothing
  • Make it reproducible. Anyone should be able to rerun the pipeline on an old commit and get the same result

CI/CD takeaways

If you remember five things
  • It is about releasing software: consistent, reproducible, standardised
  • Every change to production comes from a pipeline. No exceptions, no manual fixes
  • Pipelines are triggered by git events, so you can go back in time and reverse a mistake
  • It defines how your team collaborates, and how quickly you can respond to a problem
  • Get it wrong and you lose time and money continuously. Get it right once and it works for you every day
How this is done will vary from client to client. Keep it as simple as the team can maintain.
